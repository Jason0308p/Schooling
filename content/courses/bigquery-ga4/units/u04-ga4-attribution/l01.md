## GA4 歸因分析：UTM 參數與多通路歸因

**歸因（Attribution）** 回答的問題是：「這筆訂單，到底是哪個行銷管道帶來的？」

GA4 用 UTM 參數來記錄流量來源，再透過 session ID 把行為（events）和後續的訂單串起來。

## UTM 參數是什麼？

UTM 是 Urchin Tracking Module 的縮寫，是廣告連結後面加的追蹤參數：

```
https://example.com/products/tumbler
  ?utm_source=google
  &utm_medium=cpc
  &utm_campaign=tumbler-shopping-2025
```

| UTM 參數 | 資料集欄位 | 意義 | 範例 |
|---|---|---|---|
| utm_source | `source` | 流量來源 | google, facebook |
| utm_medium | `medium` | 媒介類型 | cpc, organic, email |
| utm_campaign | 活動名稱；本課另用 `campaign_id` 關聯 | 具體活動 | 關鍵字廣告、聖誕禮物再行銷 |

## 查看各來源流量

```sql run
SELECT
  source,
  medium,
  COUNT(DISTINCT session_id) AS sessions,
  COUNT(DISTINCT customer_id) AS logged_in_users
FROM sessions
GROUP BY source, medium
ORDER BY sessions DESC;
```

## 可重現的教學歸因模型

本課自訂「前 30 個完整日、最後有活動的 session」模型：同會員、completed 訂單，session 日期在訂單日往前 30 日（含）至訂單日前一日（含）；因 order_date 只有日期，不猜同日先後，排除訂單當日。只在 campaign_id 非 NULL 的候選中選 session_start 最大者，同時間以 session_id DESC 決勝。每單唯一歸屬，無候選不歸因。這不是 GA4 Last Click，也不處理匿名跨裝置、direct 規則或因果推論。

先在訂單粒度決定 winner，再彙總營收；COUNT(DISTINCT order_id) 不能防止 SUM(total_amount) 在多對多 JOIN 後膨脹，也不能用 SUM(DISTINCT total_amount) 去掉不同訂單的相同金額。

```sql run
WITH ranked_touches AS (
  SELECT o.order_id, o.total_amount, s.campaign_id,
    ROW_NUMBER() OVER (
      PARTITION BY o.order_id
      ORDER BY s.session_start DESC, s.session_id DESC
    ) AS touch_rank
  FROM orders o
  JOIN sessions s ON s.customer_id = o.customer_id
    AND DATE(s.session_start) >= DATE(o.order_date, '-30 days')
    AND DATE(s.session_start) < DATE(o.order_date)
  WHERE o.status = 'completed' AND s.campaign_id IS NOT NULL
),
winners AS (
  SELECT order_id, total_amount, campaign_id
  FROM ranked_touches WHERE touch_rank = 1
)
SELECT campaign_id, COUNT(*) AS attributed_orders,
  ROUND(SUM(total_amount)) AS attributed_revenue
FROM winners
GROUP BY campaign_id
ORDER BY attributed_revenue DESC, campaign_id ASC;
```

## 串聯活動花費（先各自彙總）

```sql run
WITH ranked_touches AS (
  SELECT o.order_id, o.total_amount, s.campaign_id,
    ROW_NUMBER() OVER (
      PARTITION BY o.order_id
      ORDER BY s.session_start DESC, s.session_id DESC
    ) AS touch_rank
  FROM orders o
  JOIN sessions s ON s.customer_id = o.customer_id
    AND DATE(s.session_start) >= DATE(o.order_date, '-30 days')
    AND DATE(s.session_start) < DATE(o.order_date)
  WHERE o.status = 'completed' AND s.campaign_id IS NOT NULL
),
winners AS (
  SELECT order_id, total_amount, campaign_id
  FROM ranked_touches WHERE touch_rank = 1
),
attr AS (
  SELECT campaign_id, ROUND(SUM(total_amount)) AS attributed_revenue
  FROM winners GROUP BY campaign_id
),
spend AS (
  SELECT campaign_id, ROUND(SUM(cost)) AS total_cost
  FROM ad_spend GROUP BY campaign_id
)
SELECT c.campaign_name, c.platform, sp.total_cost,
  COALESCE(a.attributed_revenue, 0) AS attributed_revenue,
  ROUND(COALESCE(a.attributed_revenue, 0) / NULLIF(sp.total_cost, 0), 2) AS roas
FROM campaigns c
LEFT JOIN attr a ON c.campaign_id = a.campaign_id
LEFT JOIN spend sp ON c.campaign_id = sp.campaign_id
ORDER BY roas DESC NULLS LAST, c.campaign_id ASC;
```

此處使用資料集全期間的完成訂單與全期間花費，只是固定範圍教學報表；正式 ROAS 需另外固定報告區間、時區、幣別、花費期間與退貨口徑，且確保窗前資料完整。靠近資料起點的訂單可能缺少早期接觸。

> [!DIALECT] **GA4 purchase 與 CRM 串接**
>
> GA4 purchase 有 transaction_id；原生匯出有 ecommerce.transaction_id、購買收入及 items。若有正確埋點，可先依交易鍵查重，再與 CRM order_id 核對。CRM 可補上訂單狀態、退款等業務資訊；不是因為 GA4「不記錄訂單」。本模擬 events 沒交易鍵，所以本課改用會員與明確回溯窗教學，不能視為逐筆交易匹配。
>
> 原生有完整時間戳時應比較真實轉換時間與接觸時間，並定義時區、同時刻決勝與 direct 規則；不要直接複製本課日期粒度假設。

## 按來源計算購買率

```sql run
WITH all_s AS (
  SELECT source, COUNT(DISTINCT session_id) AS sessions
  FROM sessions
  GROUP BY source
),
pur_s AS (
  SELECT s.source, COUNT(DISTINCT e.session_id) AS purchase_sessions
  FROM events e
  JOIN sessions s ON e.session_id = s.session_id
  WHERE e.event_name = 'purchase'
  GROUP BY s.source
)
SELECT
  a.source,
  a.sessions,
  COALESCE(p.purchase_sessions, 0) AS purchase_sessions,
  ROUND(COALESCE(p.purchase_sessions, 0) * 100.0 / NULLIF(a.sessions, 0), 2) AS purchase_rate
FROM all_s a
LEFT JOIN pur_s p ON a.source = p.source
ORDER BY purchase_rate DESC;
```

> [!TIP] **不要把教學模型稱為 GA4 Last Click**
>
> GA4 的 Paid and organic last click 與 Google paid channels last click 各有規則。本課只選候選活動 session，不代表實際廣告點擊。Data-driven attribution（DDA）是 GA4 的歸因模型，並非僅 Analytics 360 付費版可用；也不能由本課的簡單 SQL 重建。First Click 與 Linear 可用來討論一般模型，但已不是 GA4 現行可選報表模型。
