## GA4 漏斗分析：從瀏覽到購買

轉換漏斗（Conversion Funnel）是常見分析場景，但事件觸及分析不等於序列漏斗。真正序列漏斗才可描述指定步驟之間的流失；本課先做事件獨立觸及檢查。

## 電商事件的業務順序（不代表 SQL 已驗證順序）

本資料集的 5 個事件對應電商的完整購買旅程：

```
page_view → view_item → add_to_cart → begin_checkout → purchase
    ↓           ↓            ↓               ↓              ↓
  瀏覽頁面    看商品詳情    加入購物車       開始結帳        完成購買
```

## 建立獨立事件觸及表

```sql run
WITH funnel AS (
  SELECT
    CASE event_name
      WHEN 'page_view'      THEN 1
      WHEN 'view_item'      THEN 2
      WHEN 'add_to_cart'    THEN 3
      WHEN 'begin_checkout' THEN 4
      WHEN 'purchase'       THEN 5
    END AS step,
    event_name,
    COUNT(DISTINCT session_id) AS sessions
  FROM events
  WHERE event_name IN ('page_view','view_item','add_to_cart','begin_checkout','purchase')
  GROUP BY event_name
)
SELECT step, event_name, sessions
FROM funnel
ORDER BY step;
```

> [!BIZ] **為什麼用 COUNT(DISTINCT session_id)？**
>
> 同一個 session 可能觸發多次 `page_view`（使用者瀏覽了多頁），但在獨立事件觸及表中這個 session 只應計為「1 個到達 page_view 階段的 session」。
> 用 `COUNT(*)` 會把同一 session 的多次事件都計入，使事件次數被誤認為 session 數。

## 加入相鄰事件觸及數比值

```sql run
WITH funnel AS (
  SELECT
    CASE event_name
      WHEN 'page_view'      THEN 1
      WHEN 'view_item'      THEN 2
      WHEN 'add_to_cart'    THEN 3
      WHEN 'begin_checkout' THEN 4
      WHEN 'purchase'       THEN 5
    END AS step,
    event_name,
    COUNT(DISTINCT session_id) AS sessions
  FROM events
  WHERE event_name IN ('page_view','view_item','add_to_cart','begin_checkout','purchase')
  GROUP BY event_name
),
funnel_with_rate AS (
  SELECT
    step,
    event_name,
    sessions,
    LAG(sessions) OVER (ORDER BY step) AS prev_sessions
  FROM funnel
)
SELECT
  step,
  event_name,
  sessions,
  ROUND(sessions * 100.0 / NULLIF(prev_sessions, 0), 1) AS step_reach_ratio
FROM funnel_with_rate
ORDER BY step;
```

> [!DIALECT] **BigQuery GA4：事件觸及分析**
>
> 原生匯出需處理巢狀欄位；以下仍只計獨立事件觸及，先取出 `event_params`：
>
> ```sql
> -- BigQuery：先抽取複合 session 鍵，再計獨立事件觸及
> WITH sessions AS (
>   SELECT
>     user_pseudo_id,
>     (SELECT value.int_value FROM UNNEST(event_params) WHERE key='ga_session_id') AS session_id,
>     event_name
>   FROM `project.dataset.events_*`
>   WHERE event_name IN ('page_view','view_item','add_to_cart','begin_checkout','purchase')
> )
> SELECT
>   event_name,
>   COUNT(DISTINCT CONCAT(user_pseudo_id, '-', CAST(session_id AS STRING))) AS sessions
> FROM sessions
> GROUP BY event_name
> ```

## 按裝置拆分觸及

```sql run
SELECT
  s.device,
  e.event_name,
  COUNT(DISTINCT e.session_id) AS sessions
FROM events e
JOIN sessions s ON e.session_id = s.session_id
WHERE e.event_name IN ('page_view', 'add_to_cart', 'purchase')
GROUP BY s.device, e.event_name
ORDER BY s.device, e.event_name;
```

## 序列漏斗需要額外條件

上面的 GROUP BY、LAG 與裝置拆分都只是獨立事件觸及表；step 只是展示順序。不同階段可能不是同一群 session，比值甚至可能超過 100%，不能當作流失率或證明 UX 原因。

真正的封閉序列漏斗需先固定分析單位（本課可用 session_id），選定第一步，再於同一 session 找出時間嚴格晚於已選前一步的下一事件，逐步篩出合格集合；還需定義時間窗、同時間事件決勝與是否容許中間插入其他事件。不要直接對每類事件各取 MIN 後就宣稱完成，重複事件可能產生錯配。本課練習刻意不實作這種序列條件。
