## GA4 資料結構：sessions 與 events

GA4 把所有使用者行為分成兩層：**工作階段（Session）** 和 **事件（Event）**。
每一次造訪網站是一個 session，session 內的每個動作（點擊、加入購物車、購買）是一個 event。

## 本課程資料集 vs GA4 BigQuery 匯出格式

本課使用的 `sessions` 和 `events` 表，是**教學用模擬資料**，不是原生匯出的無損攤平版本：

| 本課資料集欄位 | GA4 BigQuery 匯出對應欄位 | 說明 |
|---|---|---|
| `sessions.session_id` | 原生需 user_pseudo_id + ga_session_id | 本課已提供唯一鍵，原生 ga_session_id 單獨不唯一 |
| `sessions.customer_id` | `user_id` | 已登入使用者才有值 |
| `sessions.session_start` | `event_timestamp`（session_start 事件） | 工作階段開始時間 |
| `sessions.source` | `session_traffic_source_last_click` 對應來源子欄位 | 教學工作階段來源，非一對一轉換 |
| `sessions.medium` | `session_traffic_source_last_click` 對應媒介子欄位 | 教學工作階段媒介 |
| `sessions.device` | `device.category` | 裝置類型 |
| `sessions.landing_page` | `event_params`（page_location） | 到達頁 URL |
| `events.event_name` | `event_name` | 事件名稱 |
| `events.event_time` | `event_timestamp` | 事件時間戳 |
| `events.product_id` | `items.item_id`（REPEATED items） | 相關商品 |
| `events.value` | `event_params`（value） | 事件金額 |

> [!DIALECT] **BigQuery 原生格式：巢狀的 event_params**
>
> 在真實 GA4 BigQuery 匯出中，`page_location`、`value`、`ga_session_id` 等參數**不是獨立欄位**，而是存在 `event_params` 陣列（ARRAY of STRUCT）中：
>
> ```sql
> -- BigQuery 語法：UNNEST 展開 event_params 陣列
> SELECT
>   event_name,
>   ep.value.string_value AS page_location
> FROM `project.dataset.events_*`,
>   UNNEST(event_params) AS ep
> WHERE ep.key = 'page_location'
> ```
>
> 本課的攤平格式讓你先學懂業務邏輯，後面的 DIALECT 區塊會持續說明如何轉換為 BigQuery 寫法。

## 查看資料集結構

先確認 sessions 表的欄位和資料長相：

```sql run
SELECT
  session_id,
  customer_id,
  session_start,
  source,
  medium,
  device,
  landing_page
FROM sessions
LIMIT 5;
```

再看 events 表：

```sql run
SELECT
  event_id,
  session_id,
  event_name,
  event_time,
  product_id,
  value
FROM events
LIMIT 10;
```

> [!BIZ] **為什麼要分成 sessions 和 events？**
>
> 一個 session 可以觸發多個 events（例如：瀏覽 3 頁 + 加入購物車 + 購買）。
> 用兩張表分開儲存，可以靈活做「session 層級」（整體流量）和「event 層級」（具體行為）的分析。

## 事件類型一覽

```sql run
SELECT
  event_name,
  COUNT(*) AS event_count,
  COUNT(DISTINCT session_id) AS session_count
FROM events
GROUP BY event_name
ORDER BY event_count DESC;
```

五種事件對應 GA4 的標準事件：

| event_name | GA4 標準事件 | 觸發時機 |
|---|---|---|
| `page_view` | `page_view` | 每次頁面載入 |
| `view_item` | `view_item` | 瀏覽商品詳情頁 |
| `add_to_cart` | `add_to_cart` | 加入購物車 |
| `begin_checkout` | `begin_checkout` | 開始結帳流程 |
| `purchase` | `purchase` | 完成購買 |

> [!TIP] **session_id 是連接兩張表的關鍵**
>
> `events.session_id` 是 `sessions.session_id` 的外鍵。
> 要做「按裝置拆分的事件觸及」，就需要 JOIN 兩張表：
> ```sql
> SELECT s.device, e.event_name, COUNT(DISTINCT e.session_id) AS sessions
> FROM events e
> JOIN sessions s ON e.session_id = s.session_id
> GROUP BY s.device, e.event_name;
> ```

## 流量來源分布

```sql run
SELECT
  source,
  medium,
  COUNT(DISTINCT session_id) AS sessions
FROM sessions
GROUP BY source, medium
ORDER BY sessions DESC;
```

> [!DIALECT] **三種來源範圍不能混用**
>
> - traffic_source：首次取得使用者的來源，不是本次 session 來源。
> - collected_traffic_source：事件收集時帶入的來源資料，不是已完成工作階段歸因的結果。
> - session_traffic_source_last_click：工作階段最後接觸歸因資料，依可用的 manual_campaign、google_ads_campaign 或 cross_channel_campaign 等子欄位選用；需檢查歷史資料與欄位可用性。
>
> 本課 source/medium 是預先給定的模擬工作階段維度，不能宣稱等同 collected_traffic_source。

## 商品與交易的粒度

原生商品放在 repeated items 陣列；UNNEST(items) 會讓一個事件展開成多列，計事件或訂單營收前應先回到事件／交易粒度，避免重複加總。purchase 透過 transaction_id 記錄唯一交易；匯出可用 ecommerce.transaction_id 與訂單系統核對，不是「GA4 不記訂單」。本課 events 沒有 transaction_id，不能假設它能與 orders 逐筆匹配。
