## 多步驟 CTE 與可讀性

一個查詢可以定義多個 CTE，用逗號分隔。後面的 CTE 可以引用前面的 CTE——這讓複雜分析變成一系列清晰的「計算步驟」。

---

## 語法：多個 CTE

```sql
WITH
  step_one AS (
    SELECT ...
  ),
  step_two AS (
    SELECT ...
    FROM step_one     -- 可以引用前面的 CTE
    WHERE ...
  )
SELECT ...
FROM step_two;
```

每個 CTE 之間用逗號隔開，最後一個 CTE 後面**沒有逗號**，直接接 `SELECT`。

---

## 範例 1：兩個 CTE——月營收結構（含環比準備）

```sql run
-- 先算月營收，再標示是否高於前期（預備 LAG 的概念）
WITH monthly_revenue AS (
  SELECT
    strftime('%Y-%m', order_date) AS month,
    ROUND(SUM(total_amount), 0)   AS revenue
  FROM orders
  WHERE status = 'completed'
  GROUP BY month
),
revenue_with_rank AS (
  SELECT
    month,
    revenue,
    -- 用 ROW_NUMBER 標示順序，之後學 LAG 可直接替換
    ROW_NUMBER() OVER (ORDER BY month) AS month_rank
  FROM monthly_revenue
)
SELECT
  month,
  revenue,
  month_rank
FROM revenue_with_rank
ORDER BY month;
```

> [!TIP]
> 這個範例故意把「算月營收」和「加排名」拆成兩個 CTE。現在看起來有點多此一舉，但等你加入 LAG 或 YoY 比較時，這個結構讓你只需要修改 `revenue_with_rank`，不用碰 `monthly_revenue`。**CTE 讓程式碼容易修改，是它最大的價值之一。**

## 範例 2：三個 CTE——會員消費分層

```sql run
-- CTE 1: 計算每位會員的 completed 訂單總消費
-- CTE 2: 根據消費金額分層
-- 外層: 彙總各層人數和平均消費
WITH customer_spending AS (
  SELECT
    customer_id,
    SUM(total_amount) AS total_spent
  FROM orders
  WHERE status = 'completed'
  GROUP BY customer_id
),
customer_tiers AS (
  SELECT
    customer_id,
    total_spent,
    CASE
      WHEN total_spent < 2000  THEN '低消費'
      WHEN total_spent < 10000 THEN '中消費'
      ELSE                          '高消費'
    END AS tier
  FROM customer_spending
)
SELECT
  tier,
  COUNT(*)                     AS customer_count,
  ROUND(AVG(total_spent), 0)   AS avg_spent,
  ROUND(MIN(total_spent), 0)   AS min_spent,
  ROUND(MAX(total_spent), 0)   AS max_spent
FROM customer_tiers
GROUP BY tier
ORDER BY avg_spent;
```

> [!BIZ]
> 會員消費分層是 RFM 分析的基礎。三個 CTE 讓邏輯一目瞭然：先算錢、再分類、再彙總。任何人接手這段 SQL 都能快速理解「我們在做什麼」——這在團隊協作中非常重要。

## 範例 3：好名字 vs 壞名字

```sql run
-- ❌ 壞的命名（看不出在做什麼）
WITH
  cte1 AS (
    SELECT customer_id, SUM(total_amount) AS v
    FROM orders WHERE status = 'completed' GROUP BY customer_id
  ),
  cte2 AS (
    SELECT customer_id, v,
      CASE WHEN v >= 10000 THEN 'H' WHEN v >= 2000 THEN 'M' ELSE 'L' END AS t
    FROM cte1
  )
SELECT t, COUNT(*) FROM cte2 GROUP BY t;
```

```sql run
-- ✅ 好的命名（讀起來像一段說明）
WITH
  customer_lifetime_value AS (
    SELECT customer_id, SUM(total_amount) AS total_spent
    FROM orders WHERE status = 'completed' GROUP BY customer_id
  ),
  customer_value_tier AS (
    SELECT
      customer_id,
      total_spent,
      CASE
        WHEN total_spent >= 10000 THEN '高消費'
        WHEN total_spent >= 2000  THEN '中消費'
        ELSE                           '低消費'
      END AS tier
    FROM customer_lifetime_value
  )
SELECT tier, COUNT(*) AS customer_count
FROM customer_value_tier
GROUP BY tier
ORDER BY tier;
```

> [!WARN]
> **CTE 命名原則**：
> - 用「這個 CTE 代表什麼」命名，不用 `cte1`、`tmp`、`t`
> - 動詞開頭也可以：`filtered_orders`、`aggregated_revenue`
> - 避免縮寫：`clv` 不如 `customer_lifetime_value` 清楚
> - 3–4 個 CTE 以內通常是合理範圍；超過 5 個要考慮是否需要建立暫存表或 View

---

## 何時拆成多個 CTE，何時不拆？

**應該拆的情況：**
- 同一段邏輯需要在查詢中被引用超過一次
- 有明確的「先做 A，再做 B」步驟
- 單一查詢超過 20 行難以閱讀

**不需要拆的情況：**
- 邏輯簡單，一個 JOIN + WHERE 就能表達
- 拆開後每個 CTE 只有兩行，反而製造更多噪音

> [!DIALECT]
> **多 CTE 語法**：SQLite、PostgreSQL、BigQuery 語法完全相同——多個 CTE 以逗號分隔，最後一個不加逗號。
>
> **PostgreSQL 特有**：每個 CTE 可以加 `MATERIALIZED` 或 `NOT MATERIALIZED` 提示，控制是否實體化中間結果。預設在 PostgreSQL 12 以前是 MATERIALIZED（優化屏障），12 以後由優化器決定。
>
> **BigQuery**：CTE 統一被視為內聯展開，不保證實體化；如需暫存中間結果應用 `CREATE TEMP TABLE`。
