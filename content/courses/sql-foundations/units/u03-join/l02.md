## INNER JOIN 會丟掉資料

上一課說過，INNER JOIN 只留下**兩邊都對得上**的列。如果你想找「**沒有**對上的」，INNER JOIN 做不到，因為那些列早就被丟掉了。

需求像這樣：

- 「哪些會員註冊了卻從來沒買過？」
- 「哪些商品一件都沒賣出去？」
- 「哪些活動沒有帶來任何造訪？」

這種「找缺漏」的問題，要用 **LEFT JOIN**。

## LEFT JOIN：左邊全留，右邊對不到就補 NULL

```sql run
SELECT
  c.customer_id,
  c.name,
  o.order_id
FROM customers AS c
LEFT JOIN orders AS o
  ON o.customer_id = c.customer_id
ORDER BY o.order_id
LIMIT 8;
```

結果最上面幾列，`order_id` 是 **NULL**。這些就是**從來沒下過單的會員**：左邊（會員表）的列全部保留，右邊（訂單表）對不到的欄位，一律補 NULL。

| 左邊的列 | 右邊有對到嗎 | INNER JOIN | LEFT JOIN |
|---|---|---|---|
| 會員 A | 有 2 張訂單 | 留下 2 列 | 留下 2 列 |
| 會員 B | 有 1 張訂單 | 留下 1 列 | 留下 1 列 |
| 會員 C | **沒有訂單** | **整個消失** | 留下 1 列，訂單欄位是 NULL |

## 找缺漏的標準寫法

把 LEFT JOIN 後「右邊是 NULL」的列挑出來：

```sql run
SELECT c.customer_id, c.name, c.signup_date
FROM customers AS c
LEFT JOIN orders AS o
  ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;
```

**判斷「對不到」要用右表一定有值的欄位**，通常是右表的主鍵（`o.order_id`）。不要用可能本來就是 NULL 的欄位（例如 `o.coupon_code`），否則會誤判。

> [!NOTE] 這個寫法叫 anti-join
> 「左表有、右表沒有」的過濾，在資料分析面試裡很常考。記住這個模板：`LEFT JOIN ... WHERE 右表主鍵 IS NULL`。

## 陷阱 1：條件放 ON 還是放 WHERE，結果不一樣

需求：「2026 年 4 月以後註冊的新會員，每個人各有幾張**成交**訂單？沒有成交的也要列出來，顯示 0。」

**寫法 A：成交條件放在 ON**

```sql run
SELECT c.customer_id, c.name, COUNT(o.order_id) AS completed_orders
FROM customers AS c
LEFT JOIN orders AS o
  ON o.customer_id = c.customer_id
 AND o.status = 'completed'
WHERE c.signup_date >= '2026-04-01'
GROUP BY c.customer_id, c.name;
```

**寫法 B：成交條件放在 WHERE**

```sql run
SELECT c.customer_id, c.name, COUNT(o.order_id) AS completed_orders
FROM customers AS c
LEFT JOIN orders AS o
  ON o.customer_id = c.customer_id
WHERE c.signup_date >= '2026-04-01'
  AND o.status = 'completed'
GROUP BY c.customer_id, c.name;
```

比較兩個結果的**列數**：B 比 A 少。少掉的就是「沒有成交訂單」的會員，也就是你原本最想看到的那一批。

原因是**執行順序**：

1. 先做 LEFT JOIN，沒訂單的會員這時 `o.status` 是 NULL。
2. 然後才執行 WHERE，`o.status = 'completed'` 對 NULL 不成立，那些會員又被濾掉了。

等於 **WHERE 把 LEFT JOIN 變回了 INNER JOIN**。

> [!WARN] 規則
> 針對**右表**的篩選條件，如果希望「對不到的左表列也要保留」，條件要放在 `ON`，不能放在 `WHERE`。針對**左表**的條件（例如 `c.signup_date`）放 WHERE 沒問題。

## 陷阱 2：COUNT(*) 會把「沒訂單」算成 1

LEFT JOIN 後，沒有訂單的會員仍然佔**一列**（右邊全是 NULL）。所以：

```sql run
SELECT
  c.customer_id,
  COUNT(*)          AS count_star,
  COUNT(o.order_id) AS count_orders
FROM customers AS c
LEFT JOIN orders AS o
  ON o.customer_id = c.customer_id
WHERE c.signup_date >= '2026-06-01'
GROUP BY c.customer_id
ORDER BY count_orders, c.customer_id
LIMIT 5;
```

沒有訂單的會員，`COUNT(*)` 是 **1**（那一列 NULL），`COUNT(o.order_id)` 才是正確的 **0**。

> [!TIP] LEFT JOIN 之後要數「有幾筆」，一律數右表的主鍵
> 寫 `COUNT(o.order_id)`，不要寫 `COUNT(*)`。上一單元學過 `COUNT(欄位)` 不算 NULL，這裡就派上用場。

## RIGHT JOIN 和 FULL JOIN

- **RIGHT JOIN**：跟 LEFT JOIN 相反（保留右表）。實務上幾乎都把兩張表對調、改寫成 LEFT JOIN，讀起來比較一致。
- **FULL JOIN**：左右兩邊都保留。用在要同時看「兩邊各自缺什麼」的對帳情境，不常用。

> [!DIALECT] 各資料庫支援度
> | 語法 | SQLite | PostgreSQL | MySQL | BigQuery |
> |---|---|---|---|---|
> | `LEFT JOIN` | 可以 | 可以 | 可以 | 可以 |
> | `RIGHT JOIN` | 可以（3.39 版起） | 可以 | 可以 | 可以 |
> | `FULL OUTER JOIN` | 可以（3.39 版起） | 可以 | **不支援** | 可以（寫 `FULL JOIN`） |
>
> 資料庫版本不同時支援度可能有差異，不確定時改寫成兩個 LEFT JOIN 再 UNION（第 4 課會學）。
