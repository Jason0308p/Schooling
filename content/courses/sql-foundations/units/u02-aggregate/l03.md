## HAVING：篩選分組後的結果

需求：「找出下單 5 次以上的會員」。你可能會想這樣寫：

```sql
SELECT customer_id, COUNT(*) AS order_count
FROM orders
WHERE COUNT(*) >= 5          -- ❌ 錯誤
GROUP BY customer_id;
```

這會報錯：「misuse of aggregate」。原因是 **WHERE 在分組之前執行**，那時候還沒有 `COUNT(*)` 可以用。

要篩選**分組後**的結果，用 `HAVING`：

```sql run
SELECT customer_id, COUNT(*) AS order_count
FROM orders
WHERE status = 'completed'
GROUP BY customer_id
HAVING COUNT(*) >= 5
ORDER BY order_count DESC;
```

## WHERE vs HAVING

| | WHERE | HAVING |
|---|---|---|
| 篩選什麼 | 原始的每一列 | 分組後的每一組 |
| 執行時機 | 分組**之前** | 分組**之後** |
| 能不能用彙總函數 | 不能 | 能 |
| 範例 | `WHERE status = 'completed'` | `HAVING SUM(total_amount) > 10000` |

> [!TIP] 能用 WHERE 就不要用 HAVING
> `HAVING sales_channel = 'b2b'` 語法上也行，但這是在分組後才把其他通路丟掉，白白多算了。不涉及彙總的條件都放 WHERE，先把資料量減少，查詢更快、意圖也更清楚。

## SQL 的執行順序（重要）

**書寫順序**跟資料庫**實際執行的順序**不一樣：

| 執行順序 | 子句 | 做什麼 |
|---|---|---|
| 1 | `FROM` | 決定資料來源 |
| 2 | `WHERE` | 篩選原始列 |
| 3 | `GROUP BY` | 分組 |
| 4 | `HAVING` | 篩選分組 |
| 5 | `SELECT` | 算出要顯示的欄位、取別名 |
| 6 | `ORDER BY` | 排序 |
| 7 | `LIMIT` | 取前幾筆 |

這張表可以解釋很多「為什麼會報錯」：

- **WHERE 不能用彙總函數**：WHERE 在第 2 步，分組還沒發生。
- **WHERE 不能用 SELECT 取的別名**：WHERE 在第 2 步，別名在第 5 步才產生。
- **ORDER BY 可以用別名**：ORDER BY 在第 6 步，別名已經有了。

> [!DIALECT] HAVING 裡用別名
> 照執行順序，HAVING（第 4 步）不應該認得 SELECT 的別名。但 SQLite、MySQL、BigQuery 都額外允許 `HAVING order_count >= 5`；**PostgreSQL 和 SQL Server 不允許**，必須寫 `HAVING COUNT(*) >= 5`。想寫一次到處通用，就在 HAVING 裡寫完整的彙總函數。

## 實務案例：廣告活動成效

`ad_spend` 是每個活動每天一列。用 GROUP BY 把它彙總成活動層級，就是廣告後台的「活動報表」：

```sql run
SELECT
  campaign_id,
  SUM(impressions) AS impressions,
  SUM(clicks)      AS clicks,
  ROUND(SUM(cost)) AS cost,
  ROUND(SUM(clicks) * 100.0 / SUM(impressions), 2) AS ctr_pct
FROM ad_spend
GROUP BY campaign_id
ORDER BY cost DESC;
```

> [!WARN] 比率要「先加總、再相除」，不是「平均每天的比率」
> CTR 要用 `SUM(clicks) / SUM(impressions)`，不是 `AVG(clicks / impressions)`。後者會讓曝光只有 10 次的那天，跟曝光 10 萬次的那天有一樣的權重，算出來的數字是錯的。這是分析師最常犯、也最常被面試考的錯誤之一。
