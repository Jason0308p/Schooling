## Acceptance Criteria：讓「完成」有標準

開發衝刺（Sprint）結束時，PM、工程師、QA 坐下來驗收。這時最常發生的對話是：

- 工程師：「這個功能我做完了。」
- QA：「但這個情況下會出錯。」
- 工程師：「那個 Story 沒有提到這個情況。」
- PM：「我以為是 common sense...」

這個對話的根本原因：**沒有在需求階段就定義清楚「完成」的條件**。

Acceptance Criteria（AC，驗收標準）就是解方。

---

## Given / When / Then 格式

最廣泛使用的 AC 格式來自 BDD（*Behavior-Driven Development*，行為驅動開發）：

```
Given [前置條件 / 初始狀態]
When [使用者或系統的動作]
Then [預期的結果或系統反應]
```

**範例——購物車加入商品：**

```
Given 使用者已登入，且商品庫存大於 0
When 使用者點擊「加入購物車」按鈕
Then 購物車圖示的數字應 +1，且頁面頂端出現「商品已加入購物車」的提示訊息
```

---

## 為什麼這個格式有效

| 部分 | 解決的問題 |
|---|---|
| **Given** | 明確前置條件，避免「什麼情況下才適用」的爭議 |
| **When** | 明確觸發點，避免「什麼操作算觸發」的爭議 |
| **Then** | 明確驗收標準，讓 QA 知道怎麼判定通過 |

> [!TIP] 實務建議
> 一個 Story 通常需要多個 AC——至少要涵蓋**正常流程（Happy Path）**和幾個重要的**異常情況（Edge Cases）**。不需要窮舉所有情況，但關鍵的失敗情境必須明確。

---

## Edge Case 識別方法

Edge cases 是「非典型但真實存在」的情況。識別方法：

### 1. 邊界值（Boundary Values）
數量、長度、金額等數字輸入，在邊界附近往往有特殊行為。

*例：密碼長度最小 8 字元——輸入 7 個字元時系統應如何反應？*

### 2. 空值與缺失（Null & Missing）
欄位為空、資料不存在時的行為。

*例：使用者沒有上傳頭貼——其他使用者看到的是什麼？*

### 3. 並發與競爭（Concurrency）
兩個使用者同時操作同一個資源。

*例：最後一件商品，兩人同時加入購物車——誰成功？*

### 4. 權限與角色（Permissions）
不同角色在同一功能下的行為差異。

*例：普通用戶和管理員看到的按鈕是否相同？*

> [!WARN] 常見錯誤
> 最常被忽略的 Edge Case 類型：**使用者離開流程中途**。例如填到一半的表單、付款流程中的返回按鈕、瀏覽器意外關閉。這些情況都需要明確定義行為。

## 完整範例：密碼重設功能

**User Story：**
> As a registered user, I want to reset my password via email, so that I can regain access to my account if I forget my password.

**Acceptance Criteria：**

**AC1：正常流程**
```
Given 使用者輸入已註冊的 Email 地址
When 點擊「寄送重設連結」
Then 系統在 2 分鐘內發送包含重設連結的 Email，頁面顯示「Email 已寄出，請查收信箱」
```

**AC2：未註冊的 Email**
```
Given 使用者輸入未在系統中註冊的 Email
When 點擊「寄送重設連結」
Then 系統顯示「Email 已寄出，請查收信箱」（不透露該 Email 是否已註冊，防止帳號枚舉攻擊）
```

**AC3：連結過期**
```
Given 使用者收到重設連結，但在 24 小時後才點擊
When 點擊連結
Then 系統顯示「此連結已過期，請重新申請」，並提供重新申請的按鈕
```

**AC4：連結已使用**
```
Given 使用者已成功用連結重設密碼
When 再次點擊同一個連結
Then 系統顯示「此連結已失效」
```

---

## AC 的撰寫原則

1. **每個 AC 只測試一件事**——不要把多個行為塞進一個 AC
2. **用使用者語言，不用技術語言**——「系統發送 HTTP 302 redirect」不是好的 AC
3. **具體可測量**——「速度快」不如「在 2 秒內完成」
4. **涵蓋重要的失敗路徑**——不只有 Happy Path

> [!BIZ] 業務背景
> 許多團隊使用 **Definition of Done（DoD）** 作為所有 Story 共用的基礎驗收條件（例如：必須有 Unit Test、必須通過 Code Review），而各 Story 的 AC 則是功能特定的驗收條件。兩者相加才是完整的「完成」定義。
