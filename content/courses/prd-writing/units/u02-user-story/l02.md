## Acceptance Criteria：讓「完成」有標準

開發衝刺（Sprint）結束時，PM、工程師、QA 坐下來驗收。這時最常發生的對話是：

- 工程師：「這個功能我做完了。」
- QA：「但這個情況下會出錯。」
- 工程師：「那個 Story 沒有提到這個情況。」
- PM：「我以為是 common sense...」

這個對話的根本原因：**沒有在需求階段就定義清楚「完成」的條件**。

Acceptance Criteria（AC，驗收標準）就是解方。

---

## Given / When / Then 格式

最廣泛使用的 AC 格式來自 BDD（*Behavior-Driven Development*，行為驅動開發）：

```
Given [前置條件 / 初始狀態]
When [使用者或系統的動作]
Then [預期的結果或系統反應]
```

**範例——購物車加入商品：**

```
Given 使用者已登入，且商品庫存大於 0
When 使用者點擊「加入購物車」按鈕
Then 購物車圖示的數字應 +1，且頁面頂端出現「商品已加入購物車」的提示訊息
```

---

## 為什麼這個格式有效

| 部分 | 解決的問題 |
|---|---|
| **Given** | 明確前置條件，避免「什麼情況下才適用」的爭議 |
| **When** | 明確觸發點，避免「什麼操作算觸發」的爭議 |
| **Then** | 明確驗收標準，讓 QA 知道怎麼判定通過 |

> [!TIP] 實務建議
> 一個 Story 通常需要多個 AC——至少要涵蓋**正常流程（Happy Path）**和幾個重要的**異常情況（Edge Cases）**。不需要窮舉所有情況，但關鍵的失敗情境必須明確。

---

## Edge Case 識別方法

Edge cases 是「非典型但真實存在」的情況。識別方法：

### 1. 邊界值（Boundary Values）
數量、長度、金額等數字輸入，在邊界附近往往有特殊行為。

*例：密碼長度最小 8 字元——輸入 7 個字元時系統應如何反應？*

### 2. 空值與缺失（Null & Missing）
欄位為空、資料不存在時的行為。

*例：使用者沒有上傳頭貼——其他使用者看到的是什麼？*

### 3. 並發與競爭（Concurrency）
兩個使用者同時操作同一個資源。

*例：最後一件商品，兩人同時加入購物車——誰成功？*

### 4. 權限與角色（Permissions）
不同角色在同一功能下的行為差異。

*例：普通用戶和管理員看到的按鈕是否相同？*

> [!WARN] 常見錯誤
> 最常被忽略的 Edge Case 類型：**使用者離開流程中途**。例如填到一半的表單、付款流程中的返回按鈕、瀏覽器意外關閉。這些情況都需要明確定義行為。

## 完整範例：密碼重設功能

**User Story：**
> As a registered user, I want to reset my password via email, so that I can regain access to my account if I forget my password.

**Acceptance Criteria：**

**以下為教學產品的約定**：token 自系統發出時刻起有效 24 小時，以系統時間判定；提交重設時必須再次驗證。密碼政策在本例簡化為至少 8 字元，新密碼不得與目前密碼相同；實務需另訂完整密碼及安全政策。Email 的 2 分鐘指系統交付寄信服務，不保證信箱收件時間。

**AC1：申請重設（已註冊 Email）**
```
Given 使用者輸入已註冊的 Email
When 點擊「寄送重設連結」
Then 系統在 2 分鐘內將包含重設連結的 Email 交付寄信服務
And 頁面顯示「若此 Email 已註冊，將收到重設信，請查收信箱」
```

**AC2：未註冊的 Email**
```
Given 使用者輸入未註冊的 Email
When 點擊「寄送重設連結」
Then 頁面顯示與已註冊 Email 相同的文字，不寄出重設信
```
相同文字只降低從回應文字探知帳號的風險，不能保證防止帳號枚舉；回應時間、限流及其他安全控制仍需另外設計與驗證。

**AC3：完成重設（Happy Path）**
```
Given token 屬於此帳號、尚未使用且未撤銷，且提交時系統時間早於發出時刻加 24 小時
When 使用者提交符合密碼政策、與目前密碼不同且兩次輸入一致的新密碼
Then 系統更新密碼，顯示「密碼已重設，請重新登入」並提供登入入口
And 本次 token 及此帳號其他尚未使用的重設 token 均失效
```

**AC4：新舊密碼的登入結果**
```
Given 密碼已成功重設
When 使用者分別以新密碼與重設前的舊密碼嘗試登入
Then 新密碼可登入，舊密碼不可登入
```
本例不自動登入；既有登入工作階段是否撤銷需另定 AC，不能由舊密碼不可登入推論既有工作階段全數失效。

**AC5：到期整點及提交時驗證**
```
Given token 在 2026-11-01 10:00:00 UTC 發出，到期時刻為 2026-11-02 10:00:00 UTC
When 系統在到期時刻或之後驗證連結或收到重設提交
Then 拒絕重設，不變更密碼，顯示「連結已過期或失效，請重新申請」並提供重新申請入口
```
到期前（例如 09:59:59 UTC）且其餘條件均有效時可提交；恰好 10:00:00 UTC 已過期。到期前開啟頁面不代表到期後仍可提交。

**AC6：已使用、無效或被撤銷的 token**
```
Given token 已使用、已撤銷、不存在或遭竄改
When 使用者開啟連結或提交新密碼
Then 拒絕重設，不變更密碼，顯示「連結已過期或失效，請重新申請」並提供重新申請入口
```
重設成功後重複提交或以同帳號其他已失效 token 提交，也適用此條；同一 token 的並發提交最多一次成功。

**AC7：密碼輸入不合規**
```
Given token 仍有效
When 新密碼少於 8 字元、與目前密碼相同，或兩次輸入不一致
Then 拒絕更新並顯示對應錯誤，不消耗 token，允許在有效期限內修正後重試
```
QA 應至少測試 7／8 字元、到期前／恰好到期／到期後、先開頁面後到期提交及成功後重複使用。這組 AC 示範功能契約，不是完整資安規格或安全保證。

## AC 的撰寫原則

1. **每個 AC 只測試一件事**——不要把多個行為塞進一個 AC
2. **用使用者語言，不用技術語言**——「系統發送 HTTP 302 redirect」不是好的 AC
3. **具體可測量**——「速度快」不如「在 2 秒內完成」
4. **涵蓋重要的失敗路徑**——不只有 Happy Path

> [!BIZ] 業務背景
> 許多團隊使用 **Definition of Done（DoD）** 作為所有 Story 共用的基礎驗收條件（例如：必須有 Unit Test、必須通過 Code Review），而各 Story 的 AC 則是功能特定的驗收條件。兩者相加才是完整的「完成」定義。
