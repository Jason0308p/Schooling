## Revenue：觀察收入不是 MRR 或 LTV

財務分析先確認資料粒度與口徑。MRR 是有效訂閱的月度常態收入，不能直接以 invoice 的 amount_paid 或 A/B 測試收入代替。LTV 涵蓋預期整個客戶關係的價值；本資料缺少訂閱期間、流失及可預測壽命，不能估可靠 LTV。

教學模型假設 ab_tests.revenue 每筆互不重複、同幣別且可加總。真實多實驗可能重複歸因，同一交易應先以交易 ID 去重；此資料無交易 ID，不能驗證假設。收入與活躍月份涵蓋全部現有紀錄，不是固定月 ARPU。

## 各方案 ARPU 計算

以所有用戶作分母、無收入者為零；跨實驗 revenue 只有在互斥可加總假設下才是觀察收入。方案及來源差異為描述性結果，不能單獨決定投放或推論因果。

```sql run
WITH user_rev AS (
  SELECT
    u.user_id,
    u.plan,
    COALESCE(SUM(ab.revenue), 0) AS user_revenue
  FROM users u
  LEFT JOIN ab_tests ab ON ab.user_id = u.user_id
  GROUP BY u.user_id, u.plan
)
SELECT
  plan,
  COUNT(*)                                AS total_users,
  ROUND(SUM(user_revenue), 2)             AS total_revenue,
  ROUND(SUM(user_revenue) / COUNT(*), 2)  AS arpu
FROM user_rev
GROUP BY plan
ORDER BY arpu DESC;
```

## 年化每活躍用戶月收入 proxy（非 LTV）

兩張明細直接 JOIN 會造成 活躍筆數 × 收入筆數 的 fan-out。先獨立彙總才不重複加總。此 proxy 假設每筆實驗收入獨立可加總，且觀察到的每活躍月收入可固定延伸 12 個月；活躍月不是壽命，實驗收入不是訂閱帳單，因此不能稱 LTV 或用來推論值得投入多少 CAC。

```sql run
WITH activity AS (
 SELECT user_id, COUNT(DISTINCT strftime('%Y-%m', log_date)) AS active_months
 FROM daily_active GROUP BY user_id
), revenue AS (
 SELECT user_id, SUM(revenue) AS total_revenue FROM ab_tests GROUP BY user_id
), user_stats AS (
 SELECT u.user_id, u.plan, COALESCE(a.active_months,0) AS active_months,
 COALESCE(r.total_revenue,0) AS total_revenue
 FROM users u LEFT JOIN activity a ON a.user_id=u.user_id
 LEFT JOIN revenue r ON r.user_id=u.user_id
)
SELECT plan, COUNT(*) AS users, ROUND(AVG(active_months),1) AS avg_active_months,
 ROUND(SUM(total_revenue)*1.0/COUNT(*),2) AS arpu,
 ROUND(SUM(total_revenue)*1.0/COUNT(*)/NULLIF(AVG(active_months),0)*12,2) AS annualized_revenue_proxy
FROM user_stats GROUP BY plan ORDER BY annualized_revenue_proxy DESC, plan ASC;
```

## 各渠道付費轉換率與收入貢獻

以所有用戶作分母、無收入者為零；跨實驗 revenue 只有在互斥可加總假設下才是觀察收入。方案及來源差異為描述性結果，不能單獨決定投放或推論因果。

```sql run
WITH user_rev AS (
  SELECT
    u.user_id,
    u.acquisition_channel,
    u.plan,
    COALESCE(SUM(ab.revenue), 0) AS user_revenue
  FROM users u
  LEFT JOIN ab_tests ab ON ab.user_id = u.user_id
  GROUP BY u.user_id, u.acquisition_channel, u.plan
)
SELECT
  acquisition_channel,
  COUNT(*)                                                          AS total_users,
  SUM(CASE WHEN plan IN ('pro', 'enterprise') THEN 1 ELSE 0 END)   AS paid_users,
  ROUND(SUM(CASE WHEN plan IN ('pro', 'enterprise') THEN 1 ELSE 0 END)
        * 100.0 / COUNT(*), 1)                                      AS paid_rate_pct,
  ROUND(SUM(user_revenue) / COUNT(*), 2)                           AS arpu
FROM user_rev
GROUP BY acquisition_channel
ORDER BY arpu DESC;
```

> [!WARN] 非 LTV
> ARPU / 平均活躍月數 × 12 = 年化每活躍用戶月收入 proxy，沒有客戶壽命；活躍月份不等於連續訂閱月份。即使拿來排名也不能宣稱是真實 LTV 高低。常見收入型 LTV 模型「月 ARPU / 月流失率」另需穩定同質群體與固定流失假設；利潤型還需毛利、成本與折現。

> [!TIP] 防止重複 SUM
> daily_active 與 ab_tests 都是一對多，必須先各自彙總為每位用戶一列再 JOIN。COUNT(DISTINCT user_id) 修不了 SUM；SUM(DISTINCT revenue) 會合併兩筆不同但等額的合法收入。

> [!DIALECT] 日期
> SQLite 用 strftime('%Y-%m', log_date)；BigQuery 用 FORMAT_DATE('%Y-%m', date_column)。先確認時區及欄位型別。
