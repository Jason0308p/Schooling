## Revenue 營收分析

## Growth 視角：增長的最終目的是可持續的收入

獲客、留存都是手段，**Revenue** 才是 Growth 的終點。
MRR（Monthly Recurring Revenue）、ARPU、LTV 是訂閱制 SaaS 最核心的三個收入指標。

## MRR：Monthly Recurring Revenue

MRR = 每月的訂閱收入（固定方案訂閱費 × 用戶數）。
由於 AppFlow 沒有實際交易紀錄，我們用 A/B test 的 `revenue` 欄位估算，
或用方案結構推算（以方案人數代表 MRR 結構）。

```sql run
-- 各方案的用戶數與收入結構（用 A/B test 轉換金額估算 ARPU）
SELECT
  u.plan,
  COUNT(DISTINCT u.user_id)                          AS users,
  ROUND(AVG(CASE WHEN ab.revenue > 0 THEN ab.revenue END), 2) AS avg_rev_per_conversion,
  COUNT(CASE WHEN ab.converted = 1 THEN 1 END)       AS conversions
FROM users u
LEFT JOIN ab_tests ab ON ab.user_id = u.user_id
GROUP BY u.plan
ORDER BY users DESC;
```

> [!BIZ] 業務決策意義
> ARPU（Average Revenue Per User）是衡量「每個用戶平均貢獻多少收入」的指標。
> ARPU 低可能代表：付費方案定價太低、免費用戶太多、付費用戶流失率高。

## ARPU 計算

```sql run
-- 各方案的 ARPU（只算有轉換收入的用戶）
WITH user_revenue AS (
  SELECT
    u.user_id,
    u.plan,
    COALESCE(SUM(ab.revenue), 0) AS total_revenue
  FROM users u
  LEFT JOIN ab_tests ab ON ab.user_id = u.user_id AND ab.converted = 1
  GROUP BY u.user_id, u.plan
)
SELECT
  plan,
  COUNT(*)                              AS total_users,
  SUM(total_revenue)                    AS total_revenue,
  ROUND(SUM(total_revenue) / COUNT(*), 2) AS arpu
FROM user_revenue
GROUP BY plan
ORDER BY arpu DESC;
```

## LTV 估算：ARPU × 平均活躍月數

```sql run
-- 用活躍天數估算平均使用壽命，計算簡化版 LTV
WITH user_activity AS (
  SELECT
    u.user_id,
    u.plan,
    COUNT(DISTINCT strftime('%Y-%m', da.log_date)) AS active_months,
    COALESCE(SUM(ab.revenue), 0)                   AS total_revenue
  FROM users u
  LEFT JOIN daily_active da ON da.user_id = u.user_id
  LEFT JOIN ab_tests ab ON ab.user_id = u.user_id AND ab.converted = 1
  GROUP BY u.user_id, u.plan
)
SELECT
  plan,
  COUNT(*)                                               AS users,
  ROUND(AVG(active_months), 1)                           AS avg_active_months,
  ROUND(AVG(total_revenue), 2)                           AS avg_revenue_per_user,
  ROUND(AVG(total_revenue) / NULLIF(AVG(active_months), 0) * 12, 2) AS estimated_annual_ltv
FROM user_activity
GROUP BY plan
ORDER BY estimated_annual_ltv DESC;
```

> [!TIP] 常見陷阱：LTV 計算假設很多
> 上面的 LTV 是簡化估算，實際 LTV 需要考慮：churn rate、折現率、Upsell 機率等。
> 別把這個數字當精確值——用來比較「哪個方案 / 渠道的 LTV 較高」才是正確用法。

```sql run
-- Free 用戶升級到 Pro/Enterprise 的渠道分析
SELECT
  acquisition_channel,
  COUNT(*) AS total_users,
  SUM(CASE WHEN plan = 'free' THEN 1 ELSE 0 END) AS free_users,
  SUM(CASE WHEN plan IN ('pro', 'enterprise') THEN 1 ELSE 0 END) AS paid_users,
  ROUND(SUM(CASE WHEN plan IN ('pro', 'enterprise') THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 1) AS paid_rate_pct
FROM users
GROUP BY acquisition_channel
ORDER BY paid_rate_pct DESC;
```

> [!DIALECT] BigQuery / Stripe 對應做法
> **BigQuery + Stripe：** 直接 JOIN Stripe 的 `invoices` 表，用 `amount_paid` 計算真實 MRR。
> **Looker：** 建立 `user_revenue` Explore，設定 measure `sum_revenue`，報表拖拉即可。
> **Metabase：** 用 question builder 選擇 Sum of revenue、Group by plan，不需寫 SQL。
