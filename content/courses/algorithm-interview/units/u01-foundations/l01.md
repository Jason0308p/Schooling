## 面試官問 Big O，其實在問什麼？

同一段程式，10 筆資料與 10 萬筆資料能否都跑得動？先看**輸入規模變大時，主要工作會增加多快**，再決定要不要換方法。這一課先用「活動簽到代碼去重」作為同一個例子；最後再把方法遷移到排序。

先約定：`n` 是輸入 `codes` 的長度。說 `O(n)` 不是說剛好執行 n 次，而是隨 n 增長，主要工作量至多按線性尺度增長；比較時間時要先說明採用的操作成本假設。

## 從最直覺的方法開始：為什麼它會慢？

要找出不同的代碼數，可以每讀到一筆，就回頭檢查它之前有沒有出現過：

```js
function uniqueCountSlow(codes) {
  let count = 0;
  for (let i = 0; i < codes.length; i++) {
    let found = false;
    for (let j = 0; j < i; j++) {
      if (codes[j] === codes[i]) { found = true; break; }
    }
    if (!found) count++;
  }
  return count;
}
```

用 `['A', 'B', 'A', 'C']` 手跑：第一筆不用回看，第二筆最多回看 1 筆，第三筆最多 2 筆，第四筆最多 3 筆。**最壞情況**是代碼都不同，每一輪都會比到底；比較次數為 `0 + 1 + 2 + … + (n - 1)`，隨 n 呈平方成長，因此時間是 `O(n²)`。這裡的「兩層」不是魔法公式：若內層每次只做固定幾步，就不能直接說平方。

此方法只用幾個變數，額外空間 `O(1)`。它的優點是不用額外容器；缺點是大輸入時重複做了大量回看。

## 用 Set 換掉重複回看

我們真正需要知道的是「先前看過哪些代碼」。用集合保存這份資訊：

```js
function uniqueCount(codes) {
  const seen = new Set();
  for (const code of codes) seen.add(code);
  return seen.size;
}
```

仍用 `['A', 'B', 'A', 'C']`：集合從 `{}` → `{A}` → `{A,B}` → `{A,B}` → `{A,B,C}`，最後回傳 3。**每走完一筆，集合恰好包含已讀資料中的不同代碼**；這就是維持正確性的*不變量*。空輸入沒有迴圈，回傳 0。

掃描每筆一次，若以雜湊集合查找／新增的**平均操作成本**近似 `O(1)`，總時間為平均 `O(n)`；最壞情況最多保存 n 個不同代碼，額外空間 `O(n)`。這不是保證所有 JavaScript 引擎、所有輸入的 Set 操作最壞都固定時間。

> [!BIZ] 面試怎麼說
> 「我先提出不用額外空間的回看法，最壞 `O(n²)`；再用集合記已見代碼，在平均常數時間的查找假設下改為 `O(n)`，代價是 `O(n)` 額外空間。」先講**為什麼換容器**，再講複雜度。

## 遷移：排序不是免費的前置步驟

有人會先排序再去重：

```js
const sorted = [...codes].sort();
```

先複製再排序可能有助於後續線性掃描相鄰元素，但若**只想知道不同代碼數**，完整排序通常做了多餘工作。`[...codes]` 複製 n 個元素，時間 `O(n)`、額外空間 `O(n)`；面試題通常把**高效比較排序**當作 `O(n log n)` 的分析模型，合起來主要時間為 `O(n log n)`，不是 `O(n²)`，也不是因為有兩個操作就把成本相乘。JavaScript 規格沒有保證 `.sort()` 的所有實作都採同一演算法；空間至少要算上這份複本，排序內部成本另依實作而異。

### 為什麼高效比較排序常有 `n log n`？

以 *Merge Sort* 為例：先把未排序的大陣列拆成小組，直到每組只剩一個元素（天然有序），再把兩個**已排序**的小組合併。

```text
[8, 3, 5, 1, 7, 4, 6, 2]
→ [8, 3, 5, 1]  [7, 4, 6, 2]
→ [8, 3] [5, 1]  [7, 4] [6, 2]
→ [8] [3] [5] [1] [7] [4] [6] [2]
```

例如合併 `[1,5,8]` 與 `[2,3,7]` 時，只比較兩邊**目前最前面的元素**：依序取出 1、2、3、5、7，最後放入 8；因為每邊已排序，不需要讓每個元素和另一邊所有元素比較。

反向合併整棵拆分樹：

```text
第一層：4 組 × 每組合併 2 個元素 → 該層總共處理 8 個
第二層：2 組 × 每組合併 4 個元素 → 該層總共處理 8 個
第三層：1 組 × 合併 8 個元素     → 該層總共處理 8 個
```

**每一層合計**處理 n 個元素，並非每一*組*都有 n 個。資料規模每次大致減半，從 8 → 4 → 2 → 1 要拆 3 次；一般為約 `log₂n` 層。所以 `每層 O(n) × 層數 O(log n) = O(n log n)`。這是針對 Merge Sort 的推導，**不是看到任何 `.sort()` 就能證明其實作一定有此最壞保證**。

> [!WARN] 改變條件就要重新推導
> 如果每次只拆出 1 個元素與剩下的 `n-1` 個，而每層仍要處理當前規模，層數接近 n、總工作約 `n + (n-1) + … + 1`，變成 `O(n²)`。`log n` 來自**規模持續按比例縮小**，不是「用了遞迴」。
