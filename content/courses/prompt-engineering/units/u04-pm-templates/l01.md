## PM 的 Prompt 模板庫

這一課整理了 PM 最常用的四個 Prompt 模板，每個都可以直接複製使用。

---

## 模板一：PRD 功能需求起草

```
你是資深 PM，有撰寫 B2B SaaS PRD 的豐富經驗。

幫我起草一份功能需求文件初稿：

功能名稱：[智慧通知中心]
解決的問題：[描述用戶痛點，例如：用戶錯過重要系統更新，導致資料未及時同步]
相關用戶角色：[PM / 工程師 / 一般用戶]

請輸出以下結構：

## 問題定義
（說明現狀、為什麼這是需要解決的問題、不解決的後果）

## 用戶故事（3 條，As a / I want / So that 格式）

## 功能範疇
**In-Scope（這次要做）：**
**Out-of-Scope（這次不做）：**

## 驗收標準（每條 User Story 對應的 Given/When/Then）

## 成功指標
（定義這個功能上線後要追蹤哪些指標，以及成功的門檻值）

語氣：技術性但清楚，讓工程師和設計師都看得懂，避免模糊的定性描述。
```

> [!TIP] 實務技巧
> Out-of-Scope 往往比 In-Scope 更重要。明確說「這次不做 X」，能防止功能範圍在開發過程中不斷擴大（Scope Creep）。

## 模板二：會議記錄整理

```
你是專業的產品會議記錄員，擅長從混亂的對話中提取行動要點。

根據以下 [會議類型，如：產品規劃會議 / 跨部門對齊會議] 逐字稿，輸出結構化會議記錄：

[貼入逐字稿或重點筆記]

輸出格式：

## 會議基本資訊
- 日期：
- 與會人員：
- 會議目的：

## 決議事項
（條列，每點格式：**決定了什麼** + 決定原因或背景，1-2 句）

## 待辦清單
| 任務 | 負責人 | 截止日期 | 備注 |

## 未解決問題
（需要在下次會議確認、或需要更多資訊才能決定的事項）

## 下次會議
- 時間：
- 主要議題：

**請過濾掉：閒聊、重複內容、「我覺得」等非結論性發言。**
只保留有行動意義的資訊。
```

> [!WARN] 常見錯誤
> 不要用「幫我摘要這段對話」——AI 會輸出流水帳，你還要再整理。明確的格式讓輸出可以直接發給與會者。

## 模板三：用戶反饋分析

```
你是產品分析師，專注於從用戶反饋中找出可行動的洞察。

請分析以下 [X] 則用戶反饋：
[貼入評論 / 客服記錄 / 問卷回覆]

輸出：

## 問題分類表格
| 問題類型 | 出現次數 | 嚴重程度（高/中/低） | 代表性引言（直接引用） |

## TOP 3 高優先級問題
每個包含：
- 問題描述
- 影響用戶比例估計
- 可能的解法方向（1-2 個）

## 用戶最喜歡的功能（正向反饋前 3 名）
（確保改版時不要移除這些功能）

## 潛在需求洞察
（用戶沒有直接說出口、但反饋中透露的隱性需求，1-2 個）

背景：我們的產品是 [一句話描述]，目前主要用戶是 [用戶類型]。
分析時間範圍：[填入]
```

## 模板四：A/B 測試假設整理

```
你是 Growth PM，熟悉 A/B 測試設計和分析。

幫我將以下 A/B 測試想法整理成標準假設格式：

測試背景：[描述目前的問題或觀察，例如：Onboarding 完成率只有 35%]
測試想法：[你想測試的變更，例如：簡化第一步的表單欄位數量]

請輸出：

## 測試假設
格式：「如果我們 [做了什麼改變]，那麼 [目標指標] 會 [改善方向]，因為 [假設的原因]。」

## 測試設計
- 對照組（A）：
- 測試組（B）：
- 主要指標（Primary Metric）：
- 輔助指標（Guardrail Metrics，確保沒有負向影響）：
- 最小樣本量估算：[如果你提供目前每日流量，我可以計算]
- 建議測試時長：

## 成功條件
（達到什麼數字算這個測試成功？）

## 可能的反效果
（如果測試失敗，可能說明了什麼？）
```

> [!BIZ] 為什麼這個模板在工作中很有用
> 清楚的假設格式讓 A/B 測試有明確的判斷標準。很多測試失敗不是因為方法不好，而是一開始就沒有定義清楚「什麼叫成功」。
