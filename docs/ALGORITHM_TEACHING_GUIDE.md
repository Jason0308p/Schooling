# 資料結構／演算法課教學設計

參考 `Shopify_controll/big-o-ai-teaching-prompt.md` 的教學方法；不依賴該檔案作為 Schooling 執行時資產，也不照抄整份內容。

## 一課的學習動線

1. **問題與先備知識**：先說工作／面試情境、輸入輸出與 `n` 的意義；不知道哪個先備觀念會卡住，就不要急著給公式。
2. **直覺解法與瓶頸**：先給能工作的基線解，再用同一組小資料乾跑；說明重複工作是什麼。
3. **改進動機 → 步驟**：每次換資料結構或演算法，都要交代它省掉哪項工作、換來哪項成本。不中途改用另一組數據。
4. **不變量／正確性**：乾跑每一步的狀態，說出哪些條件從頭到尾必須成立。
5. **成本來源**：明確區分時間、額外空間、平均與最壞、每組與整層；先用具體數字，再推廣到 `n`。JavaScript 引擎實作沒有規格保證的地方要標明假設。
6. **反例與邊界**：空陣列、重複值、同分、負數或改變前提（例如不平均拆分）；讓學員知道哪個結論會失效。
7. **遷移與口述**：改一項條件，請學員選擇是否仍用原方法，並練習向面試官說明理由。

一課不必變成百科：只保留能支持這條因果鏈的概念；延伸內容連到下一課。不要把篇幅當作深度，避免先公布答案再讓學員機械選字。

## 三門課的分工

- **資料結構**：怎樣表達資料、哪種操作昂貴；不把 API 名稱當重點。
- **演算法**：如何從基線推導到方法、不變量、時間與空間成本。
- **題目實戰**：在原創情境中獨立選方法、乾跑與說明邊界；只給提示與參考解，不宣稱本站能自動批改 JavaScript。

## 評量與回饋

現有 MCQ 只能檢查辨識、手跑與反例推理，**不能證明會獨立寫程式或口頭解釋**。題目至少要有「改條件／找反例／分析真實程式／比較方案」中的一種；解說要指出錯誤推理斷在哪一步，而非僅重述正確選項。開放式練習可請學員先自己寫、測試並用自己的話復述，但不要假裝已自動判分。

未來若做站內互動教練，需額外設計逐題問答、分層提示、第二次嘗試與最後才顯示解答的狀態流程；單靠靜態課文和 MCQ 無法實現自適應教學。

## 上線前檢查

- 課文與題目共用同一個例子，沒有前後不一致的輸入／結果。
- 題幹的前提足以得到唯一答案；選項不靠含糊措辭湊四選一。
- 代碼範例至少在 Node 實跑一次空輸入、正常、反例；複雜度說明與實作一致。
- 保留所有已發布 ID；跑 `node tools/validate-content.mjs` 與 `npm test`，新題在瀏覽器測答錯與答對。
